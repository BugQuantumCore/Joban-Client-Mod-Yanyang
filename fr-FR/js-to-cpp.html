Migration JS → C++

Porter un script JS existant en script natif C++. Les deux pipelines partagent des sémantiques d’enveloppe quasi un-un — le portage consiste surtout à renommer et remettre en forme, pas à réécrire.

Pourquoi migrer

Lisez d’abord ces deux pages

Avant de porter, lisez Modèle de script et cycle de vie (create / render / dispose + State par instance, totalement isomorphes des deux côtés) et Premiers pas en JS — cette page ne couvre que les différences entre les deux côtés.

  • Un seul marshalling au lieu de centaines d’appels réflexifs : côté JS, chaque lecture de champ est un appel inter-langage ; côté C++, l’instantané entier est un POD plat que le script lit comme de la mémoire ordinaire.
  • Zéro pression sur le GC : plus d’objets enveloppes ni de chaînes boxed ; les enregistrements de dessin sont alloués par bump dans une arène.
  • Garde-fou contre les plantages : un module fautif se désactive lui-même (native script faulted: module disabled) — le jeu ne plante jamais.
  • Les nouveautés arrivent d’abord en natif : teinte / émissivité / translucidité des modèles, point d’extension de signalisation, et les trois types de scripts de blocs passage à niveau / machine à billets / haut-parleur (ABI 16).
  • Quand rester en JS : scripts jetables, pas de chaîne de compilation sous la main, ou itération très rapide — voir le tableau comparatif dans la vue d’ensemble.

Cycle de vie et enregistrement

Les trois fonctions du cycle de vie deviennent des surcharges virtuelles ; l’état inter-images passe des variables de fermeture à la structure State. Choisissez la macro d’enregistrement selon le type de script — la déclaration dans le pack de ressources emprunte le même pipeline que les entrées JS.

JavaScriptC++Remarques
function create(ctx, state, pids)void create(PidsContext& ctx, State& state, const Pids& pids) overrideexécuté une fois avant le premier rendu
function render(ctx, state, pids)void render(...) overrideà chaque image (même cadence au mieux que JS)
function dispose(ctx, state, pids)void dispose(...) overridenettoyage au retrait de l’instance
variable de fermeture survivant aux imagesmembre de la structure Stateallouée par l’hôte, placement-new ; le paramètre modèle de la classe de base est votre type State
SCRIPT_INPUT JSONapi.input()mtr::Api (ABI 8+), la même entrée déclarée dans le pack

Enregistrement : MTR_REGISTER_PIDS_SCRIPT(MyScript) — véhicules / ascenseurs / décorations / portes palières / passages à niveau / machines à billets / haut-parleurs utilisent MTR_REGISTER_VEHICLE_SCRIPT / _LIFT_ / _EYECANDY_ / _PSD_ / _LEVEL_CROSSING_ / _FARE_MACHINE_ / _ANNOUNCEMENT_. Un id de script par module, déclaré dans mtr_custom_resources.json exactement comme les entrées JS (les règles de classification scriptLocations sont inchangées).

Sans équivalent (porter à la main)

Pas de jumeau

Ces facilités JS n’ont pas de correspondance un-un côté natif — réécrivez-les selon la colonne de droite ; le convertisseur laisse lui aussi un TODO à chacun de ces endroits.

Convertisseur semi-automatique

Le SDK embarque tools/js2cpp.py (bibliothèque standard pure, zéro dépendance) pour automatiser les parties mécaniques des tableaux ci-dessus :

python3 native/tools/js2cpp.py input.js -o output.cpp --id mypack:pids --kind pids

Il applique tous les renommages de cette page, convertit les forEach en boucles à index, les chaînages TextWrapper en chaînages mtr::Text, les accès de propriété en accesseurs, déplace les variables manifestes de portée module dans des champs State (inférence de type + réécriture du préfixe state.), et réécrit les usages élémentaires de Math / console ; les parties réellement dynamiques ne sont jamais réécrites en silence — elles reçoivent toutes un marqueur TODO.

Résultat attendu : un squelette qui compile en l’état plus une poignée de TODO. Compilez ensuite selon Compilation et itérez en jeu avec le rechargement à chaud.

Exemple de bout en bout

Le même script PIDS « première arrivée », écrit des deux façons :

let PREFIX = "";                 // constante de portée module

function create(ctx, state, pids) {
    state.ticks = 0;             // état par instance
}

function render(ctx, state, pids) {
    state.ticks++;
    const next = pids.arrivals().get(0);
    const dest = next ? next.destination : "Aucun train";

    new Text(PREFIX + dest)
        .pos(0, 0).size(pids.width, 14)
        .centerAlign().draw(ctx);
}
#include <mtr/script.hpp>

struct FirstArrivalState { int ticks = 0; };   // état par instance

struct FirstArrival : mtr::PidsScript<FirstArrivalState> {
    static constexpr auto ID = "example:first-arrival";

    void render(mtr::PidsContext& ctx, FirstArrivalState& state,
                const mtr::Pids& pids) override {
        state.ticks++;

        const auto arrivals = pids.arrivals();
        mtr::StrView dest = arrivals.size() > 0
            ? arrivals.at(0).destination() : mtr::StrView{"Aucun train"};

        mtr::Text::create()
            .text(dest.str().c_str())
            .pos(0, 0).size(pids.width(), 14)
            .center_align().draw(ctx);
    }
};

MTR_REGISTER_PIDS_SCRIPT(FirstArrival)
  • La logique correspond ligne à ligne : le test null sur get(0) devient une garde size() > 0 (le get JS retourne null hors limites, le at C++ lève — voir Instantanés de données pour la sémantique).
  • Les horloges façon Timing.now() deviennent toutes des accesseurs d’instantané ; la variable de fermeture state.ticks reste dans State telle quelle.
  • Côté pack de ressources : pendant la migration, les versions JS et C++ peuvent cohabiter dans le même pack sous des ids indépendants (scriptLocations accepte les déclarations mixtes) ; une fois les sorties vérifiées écran par écran, basculez l’entrée côté C++ — formats de déclaration dans Empaquetage.
