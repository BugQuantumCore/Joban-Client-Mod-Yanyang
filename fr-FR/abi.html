ABI C et services de l’hôte

Le contrat complet entre le module et l’hôte. Avec les classes de base et macros d’enregistrement de script.hpp, tous ces détails sont pris en charge par le SDK — cette page s’adresse à ceux qui veulent comprendre la frontière, écrire des pilotes de test ou diagnostiquer des problèmes de chargement.

Exportations du module

Chaque bibliothèque de script exporte 7 fonctions C (mtr_native.h ; les macros d’enregistrement les génèrent toutes automatiquement) :

ExportationDescription
uint32_t mtrNativeAbiVersion()retourne la version d’ABI de compilation (actuellement 10) ; l’hôte refuse les versions incompatibles — même politique de rechargement sur différence de version que JCM applique aux scripts JS
const char* mtrScriptType()"vehicle" / "pids" / "eyecandy" / "lift"
const char* mtrScriptId()id du script (doit correspondre à la déclaration du pack de ressources)
size_t mtrStateSize()taille du bloc d’état par instance ; l’hôte en alloue un par instance
void mtrInit(const JcmFrameInput*)appelée une fois juste après l’allocation du bloc d’état par l’hôte, construit State par placement-new (requis depuis ABI 6 ; si l’hôte omet l’appel, le module retombe sur une construction paresseuse)
int32_t mtrCreate / mtrRender / mtrDispose(const JcmFrameInput*, …)points d’entrée du cycle de vie ; retours : 0 succès, -1 entrée nulle, -2 ABI incompatible, -3 type de ressource inadéquat. L’hôte appelle en série, instance par instance, sur un unique thread d’arrière-plan par module

Entrée et sortie de frame

JcmFrameInput (hôte → module)

typedef struct JcmFrameInput {
    uint32_t abi_version;              /* version ABI négociée */
    int32_t  resource_kind;            /* MtrResourceKind : vehicle/pids/eyecandy/lift */
    const void* snapshot;              /* le Jcm*Snapshot correspondant */
    void*    state;                    /* bloc d'état par instance, alloué par l'hôte */
    size_t   state_size;
    const struct JcmHostServices* host;/* services de l'hôte appelables depuis le thread de rendu */
} JcmFrameInput;

Conventions internes de l’instantané : tous les champs *_offset sont des décalages en octets relatifs au premier octet de l’instantané ; string_pool_offset/len décrit l’emplacement du pool de chaînes UTF-8 partagé. Les enveloppes du SDK font tout l’adressage à votre place.

JcmFrameOutput (module → hôte)

La sortie est un flux plat d’enregistrements + cinq zones — une « zone » (arena) est un grand bloc de mémoire préalloué, alloué séquentiellement au fil de la frame puis restitué d’un bloc à sa fin — dès que mtrRender retourne, l’hôte lit la sortie et récupère la frame (le double tampon entre modules est assuré par l’hôte) :

ZoneContenuCapacité (défaut SDK)
recordsenregistrements de dessin en ordre séquentiel (longueur variable, parcourus par pas de record_size)256 entrées
matrix_arenaflux de matrices (4×4 en ordre colonne, 16 float par matrice)128 jeux
string_arenaflux de chaînes UTF-8 (id de texture, textes, id de son…)32 Ko
pixel_arenaflux de pixels BGRA8 (téléversement de textures)1 Mo au départ, croît à la demande jusqu’à 16 Mo, se rétracte après les pics
float_arenaflux de float (boîtes de collision voxel, etc.)1024 valeurs

Depuis ABI 9, la sortie donne aussi la capacité complète de chaque zone — l’hôte ne crée qu’un seul ByteBuffer par zone, dont seul le limit change à chaque frame ; plus aucune allocation de cinq objets d’emballage par frame.

Enregistrements de dessin

Chaque enregistrement commence par un JcmRecordHeader{kind, flags, record_size}, en ordre séquentiel à longueur variable. flags porte des commutateurs au niveau de l’enregistrement : actuellement, seul MTR_RECORD_FLAG_NATURAL_LIGHT est défini (l’option natural_light() de Text / Texture / Rect — prend la lumière du monde au lieu de la luminosité maximale de rendu). Cet octet a été promu sur place depuis un octet de padding : les modules compilés avec d’anciens SDK écrivent toujours 0 et les anciens hôtes l’ignorent — compatibilité binaire dans les deux sens, sans saut de version d’ABI. 8 types :

kindStructureUsage / appel JS reflété
JCM_DRAW_TEXTJcmDrawTexttexte PIDS / générique (alignement champ par champ avec TextWrapper : alignement, mode de débordement, marquee, ordre z, couche, id de police)
JCM_DRAW_TEXTUREJcmDrawTexturefacette texturée (UV, teinte, ordre z)
JCM_DRAW_MODELJcmDrawModelmodèles de voiture / bogie / eyecandy (handle de modèle de l’hôte + jeu de matrices de pose)
JCM_DRAW_SOUNDJcmDrawSoundson spatialisé (décalage en coordonnées locales de la voiture)
JCM_DRAW_LOCAL_SOUNDJcmDrawSoundannonce de station (audible uniquement des joueurs à bord)
JCM_DRAW_TEXTURE_UPLOADJcmDrawTextureUploadtéléversement de pixels GraphicsTexture (BGRA8 + rectangle modifié)
JCM_DRAW_OUTLINE_SHAPEJcmDrawShapecontour / boîte de collision d’eyecandy (6 float par boîte ; hauteur de collision plafonnée à 1,5 bloc)
JCM_DRAW_BLOCK_EVENT—poignée de main de l’événement onBlockUse d’eyecandy

Pour rejouer ces enregistrements, l’hôte emprunte exactement le même chemin de code de rendu que les scripts JS (PIDSDrawCall / ScriptRenderManager) — le résultat à l’écran est identique.

Services de l’hôte

JcmHostServices est une table de pointeurs de fonctions (in->host), appelable depuis le thread de rendu. Sur les anciens hôtes, les emplacements ajoutés récemment valent null ; testez la vacuité avant l’appel pour rétrograder proprement :

ServiceDepuisDescription
acquire_model / release_modelABI 1cycle de vie des handles de modèles JSON (miroir des handles ModelJS)
create_texture / release_textureABI 1cycle de vie de GraphicsTexture (miroir de la classe Java)
rasterize_textABI 1rappel de rastérisation TTF de l’hôte (CJK, etc.), écrit en BGRA8 dans le tampon de l’appelant ; retourne -1 si la police ne couvre pas le point de code (retombez alors sur la police bitmap intégrée)
logABI 1canal console.log / console.error
acquire_quad_modelABI 4l’hôte construit une facette texturée (4 sommets + UV + étape de rendu + handle de texture) — l’équivalent natif des modèles de slot du DisplayHelper JS ; sommets en espace modèle, UV origin au coin supérieur gauche de la texture, y vers le bas. Un pilote headless retourne -1 : sautez alors le dessin
measure_font_text / draw_font_textABI 7métrique et rastérisation sur ligne de base des polices de ressource (même police, mêmes sémantiques de compression et de clipping que le Graphics2D de JS ; bornes de la zone modifiée en paramètre de sortie)
invoke_apiABI 8canal sous-jacent de mtr::Api : requête JSON UTF-8 en entrée, résultat écrit dans un tampon local au thread (valable jusqu’au prochain appel)
defer_freeABI 10confie un gros bloc de mémoire déjà mort au thread de récupération en arrière-plan de l’hôte (détails dans Performance et débogage)

Évolution des versions d’ABI

L’hôte accepte les modules ABI 6–11 (chacun est alimenté selon la disposition de son époque et rapporte son propre numéro d’ABI). Compiler avec le SDK actuel produit des modules ABI 10 :

ABIApports
6mtrInit() : l’hôte doit construire l’objet d’état (un bloc rempli de zéros est un comportement indéfini pour les types non triviaux)
7métrique des polices de ressource + rastérisation de texte sur ligne de base ajoutées aux services de l’hôte
8invoke_api (canal vers l’intégralité des API Java), instantané ascenseur, mode typé des correspondances ; une bibliothèque ABI 8 exige un hôte JCM 2.3.0-beta-2.yanyang.7 ou supérieur
9id de type de transport canonique des correspondances / véhicules (extension MAGIC MTR) ; l’hôte cesse de copier l’instantané à chaque frame, capacité des zones en paramètre de sortie
10crochet de récupération différée defer_free (libération hors des threads JVM des gros tampons appartenant au script)
11door_direction sur l’instantané véhicule (sens d’ouverture des portes 0..3 — l’ancien octet _pad0 promu sur place ; disposition et taille inchangées, les anciens modules continuent de fonctionner)
Pourquoi refuser les anciens hôtes

La table de pointeurs de fonctions croît avec l’ABI : un module récent appellera des emplacements absents d’un hôte ancien. L’hôte choisit la disposition de structure et le mode d’alimentation selon le numéro d’ABI rapporté par le module, et refuse le chargement en cas de discordance — une stratégie d’échec rapide délibérée.

Couche de transport (interne à l’hôte, invisible pour les scripts)

Depuis 2.3.0-beta-2.yanyang.6 (layout v2), le mod est totalement dépourvu de JNI : deux plans d’appel portent l’intégralité du trafic inter-langages — le plan Panama FFM (JDK 22+, libraryLookup + downcalls jcm_* + vtable d’upcalls) et le plan de scrutation en mémoire partagée (tout JDK ≥ 16 ; un thread poller d’arrière-plan démarré par le constructeur du pont découvre la région par une poignée de main via le système de fichiers, tout est servi via des pages partagées). Le code des scripts n’en a absolument pas conscience — le module ne voit que l’ABI C décrite ci-dessus.
