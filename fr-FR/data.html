Instantanés de données

Des données en lecture seule, marshallées par l’hôte une fois par frame. Tous les accesseurs sont de simples lectures mémoire — zéro JNI, zéro réflexion, zéro boxing.

Mécanique des instantanés

Au début de chaque frame, l’hôte marshalle en une seule fois les données de l’instance en un instantané POD (en-tête de longueur fixe + pools de tableaux de longueur variable + pool de chaînes UTF-8), qu’il transmet à mtrRender avec le pointeur du bloc d’état. Les enveloppes typées du SDK (mtr::Vehicle, mtr::Pids, mtr::Lift, mtr::EyeCandy) fournissent sur ce bloc mémoire des accesseurs homonymes de ceux du Wrapper JS :

  • Les chaînes sont retournées sous forme de mtr::StrView (data + len) ; convertissez avec .str() en std::string et testez la vacuité avec .empty() ; la vue n’est valable que durant l’appel render en cours.
  • Un index hors limites lève std::out_of_range (sémantique identique à l’IndexOutOfBounds côté Java).
  • Ne conservez pas les pointeurs d’instantané ni les enveloppes d’une frame à l’autre.
Couverture

L’instantané couvre les champs lus à haute fréquence. Les données absentes de l’instantané (réseau, fichiers, interfaces profondes des gestionnaires de rendu, etc.) s’accèdent via mtr::Api — un canal basse fréquence, à ne pas utiliser sur le chemin chaud.

Vehicle (véhicule)

Terminologie : train (MTR 3) → vehicle (MTR 4)

MTR 4 désigne uniformément les véhicules par vehicle (clé de déclaration vehicleScripts côté pack de ressources, VehicleWrapper côté Java) ; la classe d’enveloppe de données de ce SDK est donc nommée mtr::Vehicle. Les versions antérieures du SDK la nommaient mtr::Train, selon l’usage de MTR 3 ; ce nom est aujourd’hui conservé comme alias de compatibilité source — les deux écritures compilent et se comportent strictement de la même façon.

Remarque : le nom mtr::Vehicle est présent dans les sources du SDK du dépôt et sera livré avec le zip de la prochaine version ; si votre projet utilise le zip du SDK yanyang.7 (ou antérieur), référencez cette classe par mtr::Train (les deux graphies compilent avec le nouveau SDK).

Modes et types de transport

Deux axes complémentaires, qui retournent exactement les mêmes valeurs que getTransportMode() / getTransportType() côté JS ; des scripts écrits dans des langues différentes peuvent donc partager la logique de mise en page :

  • Mode (énumération mtr::TransportMode) : UNKNOWN / TRAIN / BOAT / CABLE_CAR / AIRPLANE, couvrant les quatre catégories de véhicules de base.
  • Type (id sous forme de chaîne, constantes mtr::transport_type) : le nom en minuscules du mode de base ("train", "boat", "cable_car", "airplane"), augmenté des types de ligne étendus de MAGIC MTR Addon train_normal / train_light_rail / train_high_speed / train_metro / train_bus / train_tram / train_sbahn ; en cas d’échec d’analyse : "unknown" ou vue vide (données de serveurs anciens).
if (vehicle.getTransportType() == mtr::transport_type::TRAIN_METRO) { /* ... */ }

for (int i = 0; i < stop.interchange_count(); i++) {
    mtr::Stop::Interchange ic = stop.interchange(i);
    if (ic.getTransportType() == mtr::transport_type::TRAIN_HIGH_SPEED) { /* ... */ }
}
Source des données

Les types MAGIC sont analysés à partir de la configuration locale lorsque l’addon est installé côté client ; si le serveur le possède mais pas le client, ils parviennent par le jeu de données synchronisé ; les serveurs anciens n’envoyant pas de métadonnées de ligne, la valeur retournée est alors vide / UNKNOWN — les serveurs équipés de ce mod peuvent fournir les métadonnées complètes des stations distantes.

Les détails de l’événement (joueur, objet en main, etc.) se lisent via Api :

mtr::Api api(ctx.input());
auto event = api.context().call("events").get("onBlockUse");
if (event.call("occurred").as<bool>()) {
    auto detail = event.call("detail");
    auto player = detail.call("player");
    auto item   = detail.call("item");
}

Le contexte de dessin de l’eyecandy, EyeCandyContext, fournit draw_model(model, matrices), play_sound(sound, volume, pitch), set_outline_shape(boxes, count) et set_collision_shape(boxes, count) (6 float par boîte ; les boîtes de collision conservent la limite de hauteur de 1,5 bloc appliquée côté Java, tout dépassement est validé et journalisé par l’hôte). L’ascenseur réutilise le même type de contexte (LiftContext = EyeCandyContext).
