Scripts de véhicule

Dans MTR 4, un « véhicule » est une entrée de modèle de voiture ; le joueur assemble librement ces entrées en rames dans l’interface de la voie de garage. Le script n’est lié ni à une voiture isolée ni à la rame entière, mais à une entrée de script : l’entrée de véhicule y fait référence par scriptId, et plusieurs véhicules peuvent réutiliser le même script — composition mixte, performance et compatibilité NTE réunies.

Trois callbacks (ctx est un VehicleScriptContext, vehicle un VehicleWrapper) :

function create(ctx, state, vehicle) { /* avant le premier rendu : créer les textures, enregistrer les callbacks */ }
function render(ctx, state, vehicle) { /* à chaque frame : lire l'état, soumettre dessins et sons */ }
function dispose(ctx, state, vehicle) { /* au retrait : libérer les textures */ }

Masquer les afficheurs vanilla

Pour les véhicules bâtis sur les modèles vanilla, hideDisplayParts (MTR 4) / hide_display_cube (MTR 3) masque les blocs d’affichage de destination intégrés, à remplacer par votre propre dessin de script.

Modes de récupération des données du véhicule

MTR 4 ne synchronise que les données proches, alors que les scripts de véhicule veulent souvent les noms de stations de toute la desserte. D’où les trois niveaux de JCM (champ dataFetchMode) :

ModeComportement
SKIPDéfaut de MTR 4. Ne demande rien au serveur et reconstitue localement, au mieux, une table des arrêts — sans garantie d’exhaustivité. Suffit pour les scripts qui ne regardent que la vitesse, du genre « sonner dès que le train bouge »
ALLRécupère d’abord toute la table des arrêts, puis, id par id, les données de stations / lignes. Avant l’arrivée des données, se comporte comme SKIP ; même la table en main, Stop.station / Stop.route peuvent encore valoir null — testez la vacuité
MANDATORYComme ALL, mais le script ne démarre pas du tout tant que toutes les données ne sont pas parvenues. Valeur par défaut du format MTR 3 (les anciens scripts supposent des données immédiatement exploitables et ne tolèrent pas null)

Scripts d’eyecandy

Rattaché à une entrée de modèle de décoration MTR (Decoration Object) : le script entre en action dès qu’un bloc de décoration arborant ce modèle est rendu. Enregistrement via objects + objectScripts (l’ancien format MTR 3 se déclare dans eyecandy.json) ; isScriptControlled: true sur l’entrée de contenu masque le modèle d’origine et confie tout l’affichage au script.

Trois callbacks : ctx est un EyeCandyScriptContext, eyecandy un EyecandyWrapper.

EyeCandyScriptContext (ctx)

MembreDescription
getRenderManager(): RenderManagerréférentiel = position du bloc + décalage GUI, rotation GUI comprise
getSoundManager(): SoundManagerréférentiel = position du bloc ; le commode ctx.playSound(id, volume, pitch) joue directement au niveau du bloc
drawModel(model, matrices?)dessine le modèle (accepte aussi un DynamicModelHolder) — équivaut à getRenderManager().drawModel(...)
events(): EyecandyEventsaccès aux événements : clic droit events().onBlockUse.occurred() → traitement → events().handled() pour confirmer ; le détail de l’événement .detail().player() fournit le PlayerEntity acteur (un clic droit pinceau en main ne compte pas)
setOutlineShape(shape) / setCollisionShape(shape)contour / boîte de collision personnalisés (VoxelShape) ; sans effet tant que le pinceau est en main
setDebugInfo(...)comme pour les autres types

EyecandyWrapper (eyecandy)

Obsolète : la lecture directe des champs (eyecandy.translateX, eyecandy.prefabId, etc.) reste utilisable.

Exemple : musique en boucle qui s’atténue au clic droit

Accrochez une musique en boucle avec TickableSoundInstance.create(...) + setLoopable(true) ; dans les 5 secondes qui suivent un clic droit, setSoundVolume(0.25), puis retour à 1.0 au terme des 5 secondes ; stop dans dispose — code complet dans la documentation amont sounds.

Scripts d’ascenseur

Rattaché à une entrée d’habillage de cabine d’ascenseur : le script prend effet lorsque le joueur sélectionne cet habillage avec le rafraîchisseur d’ascenseur. Enregistrement via lifts + liftScripts ; isScriptControlled: true sur l’entrée d’habillage masque le modèle d’origine.

Trois callbacks : ctx est un LiftScriptContext, lift un LiftWrapper.

LiftScriptContext (ctx)

getRenderManager(): RenderManager (référentiel = position de base de l’ascenseur + décalage, pivotant avec l’ascenseur) · getSoundManager(): SoundManager (même référentiel) · setDebugInfo(...).

Scripts PIDS

Système indépendant

Ce système est incompatible avec PIDS Layout Editor / PIDS Modularization / PIDS JSON (EpicPuppy) ainsi qu’avec la personnalisation des écrans d’information des versions de test initiales de MTR 4 — aucun import mutuel des formats : la marche d’entrée est plus haute, mais des mises en page bien plus complexes sont possibles.

Dans le tableau pids_images de joban_custom_resources.json, un objet de préréglage portant scriptFiles ou scriptTexts devient un préréglage scripté (scriptInput / scriptRateLimit ont la même signification que pour les autres types ; Yanyang accepte aussi d’y mêler du C++ via scriptLocations, voir Entrées mixtes) :

{
    "pids_images": [
        {
            "id": "pids_demo",
            "name": "Demo Scripted PIDS",
            "scriptFiles": ["jsblock:scripts/pids_demo.js"],
            "scriptInput": { "theme": "dark" },
            "scriptRateLimit": 0.75
        }
    ]
}

Ce qui se dessine sur un PIDS, ce sont des polygones dans le monde, pas un canevas 2D — les éléments peuvent déborder de l’écran, et le clipping aux bornes de l’écran est à la charge du script (pour un clipping ou un traitement d’image vraiment complexes, dessinez dans une GraphicsTexture puis plaquez-la). L’ordre de dessin fait la hiérarchie : le dernier dessiné recouvre les précédents ; par défaut, chaque dessin est translaté d’un petit pas le long de z (0.0002) pour éviter le z-fighting — désactivable via ctx.setAutoZOrdering(false) pour passer à un zOrder() manuel (le pas se règle avec ctx.setZOrderStep(m)).

PIDSScriptContext (ctx) et PIDSBlockEntity (pids)

ctx.getRenderManager() / ctx.getSoundManager() (référentiel = position du bloc) · ctx.setAutoZOrdering(b) · ctx.setZOrderStep(m) · ctx.setDebugInfo(...).

Une texture dynamique sur un PIDS

Un PIDS accepte lui aussi une GraphicsTexture : new GraphicsTexture(pids.width, pids.height) dans create ; dans render, dessinez, upload(), puis Texture.create().texture(state.tex.identifier).size(pids.width, pids.height).draw(ctx) ; close() dans dispose — la solution de repli quand la composition de texte ne suffit plus, au prix de performance et de mémoire.

Pas besoin de script ? Remplissez uniquement les champs JSON background / color / fonts / showWeather / showClock / hidePlatform / hideRow / topPadding / textOverflowMode, etc. dans pids_images : c’est un « préréglage JSON » — suffisant pour relooker simplement, l’alternative au préréglage scripté (jamais les deux à la fois).

DisplayHelper (l’assistant multi-écrans intégré)

La solution clé en main pour les écrans multiples embarqués : après include(Resources.id("mtrsteamloco:scripts/display_helper.js")) —

let slotCfg = {
    "version": 1,
    "texSize": [2048, 1024],
    "slots": [
        { "name": "lcd_north", "texArea": [0, 0, 2048, 274],
          "pos": [[[-0.59, 2.125, -1.75], [-0.755, 2.03, -1.75],
                   [-0.755, 2.03, -3.25], [-0.59, 2.125, -3.25]]],
          "offsets": [[0, 0, -5], [0, 0, 0], [0, 0, 5], [0, 0, 10]] }
    ]
};
let dhBase = new DisplayHelper(slotCfg);

function create(ctx, state, vehicle) {
    state.rl = new RateLimit(0.05);
    state.dh = dhBase.create();          // instancie et lie la texture
}
function render(ctx, state, vehicle) {
    if (state.rl.shouldUpdate()) {
        let g = state.dh.graphicsFor("lcd_north");  // le canevas de l'emplacement (décalage automatique)
        // ... dessin AWT ...
        state.dh.upload();
    }
    for (let car of ctx.getMyCars())
        ctx.getCarRenderManager(car).drawModel(state.dh.model, null);  // à dessiner à chaque frame
}
function dispose(ctx, state, vehicle) {
    state.dh.close();
}
  • Tous les emplacements partagent une grande texture texSize ; texArea désigne la zone qu’occupe chaque emplacement (x, y, w, h).
  • pos est un tableau à trois dimensions : les quatre coins de chaque écran (haut-gauche → bas-gauche → bas-droite → haut-droite), en mètres (les unités 1/16 de Blockbench se divisent par 16), l’origine au centre du train, à hauteur de plancher, +X vers la gauche / +Y vers le haut / +Z vers l’arrière.
  • offsets duplique les écrans de même contenu (économie de texture pour les rangées de petits écrans au-dessus des portes) ; graphicsFor(name) fournit le canevas déjà décalé, graphics() la texture entière.
  • Placez le téléversement dans le RateLimit, et le dessin du modèle à l’extérieur — le modèle doit être soumis à chaque frame.
