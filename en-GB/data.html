Data snapshots

Read-only data marshalled by the host once per frame. Every accessor is a plain memory read—zero JNI, zero reflection, zero boxing.

How snapshots work

At the start of each frame the host marshals the instance's data in one go into a POD snapshot (fixed-length header + variable-length array pools + a UTF-8 string pool) and passes it to mtrRender together with the state block pointer. On top of that memory, the SDK's typed wrappers (mtr::Vehicle, mtr::Pids, mtr::Lift, mtr::EyeCandy) provide accessors with the same names as their JS counterparts:

  • Strings come back as mtr::StrView (data + len); convert with .str() to a std::string and test with .empty(); the view is valid only within the current render call.
  • Out-of-range indices throw std::out_of_range (matching the semantics of the Java side's IndexOutOfBounds).
  • Do not keep snapshot pointers or wrappers across frames.
Coverage

Snapshots cover the fields that are read at high frequency. Data that is not in the snapshot (networking, files, deep interfaces of the render manager and so on) is reached through mtr::Api—that is a low-frequency channel; do not use it on the hot path.

Vehicle

Terminology: MTR 3's train → MTR 4's vehicle

MTR 4 uniformly uses vehicle as its term (the resource pack declaration key vehicleScripts, the Java-side VehicleWrapper), so this SDK's data wrapper class is named mtr::Vehicle. Earlier SDK versions followed the MTR 3 convention and named it mtr::Train; that name is now retained as a source-compatible alias—either name compiles, and the behaviour is completely identical.

Note: the mtr::Vehicle name is in the repository's SDK sources and ships with the next release's zip; if your project uses the yanyang.7 (or earlier) SDK zip, refer to this class as mtr::Train (both spellings compile against the new SDK).

Transport modes and types

Two complementary classifications, for which the JS-side getTransportMode() / getTransportType() return exactly the same values, so scripts across languages can share layout logic:

  • Mode (the mtr::TransportMode enum): UNKNOWN / TRAIN / BOAT / CABLE_CAR / AIRPLANE, covering the four basic vehicle kinds.
  • Type (string ids, the mtr::transport_type constants): the lower-case names of the basic modes ("train", "boat", "cable_car", "airplane"), plus the extended route types from the MAGIC MTR Addon: train_normal / train_light_rail / train_high_speed / train_metro / train_bus / train_tram / train_sbahn; values that cannot be resolved become "unknown" or an empty view (old server data).
if (vehicle.getTransportType() == mtr::transport_type::TRAIN_METRO) { /* ... */ }

for (int i = 0; i < stop.interchange_count(); i++) {
    mtr::Stop::Interchange ic = stop.interchange(i);
    if (ic.getTransportType() == mtr::transport_type::TRAIN_HIGH_SPEED) { /* ... */ }
}
Data source

MAGIC types are resolved from local configuration when the client has the addon installed; when the server has it but the client does not, they arrive via a synchronised data set; old servers that send no route metadata yield empty / UNKNOWN—servers running this mod can supply complete metadata for remote stations.

Event details (player, held item and so on) are read through Api:

mtr::Api api(ctx.input());
auto event = api.context().call("events").get("onBlockUse");
if (event.call("occurred").as<bool>()) {
    auto detail = event.call("detail");
    auto player = detail.call("player");
    auto item   = detail.call("item");
}

The eyecandy drawing context EyeCandyContext provides draw_model(model, matrices), play_sound(sound, volume, pitch), set_outline_shape(boxes, count) and set_collision_shape(boxes, count) (6 floats per box; collision boxes keep the Java-side 1.5-block height limit, and anything beyond is validated and logged by the host). Lifts reuse the same context type (LiftContext = EyeCandyContext).
