Vehicle scripts

A 'vehicle' in MTR 4 is a single car model entry; players freely marshal them into trains on the siding screen. A script binds to neither a single car nor a whole train, but to a script entry: vehicle entries reference it via scriptId, and multiple vehicles can reuse the same script—mixed consists, performance and NTE compatibility all at once.

The three callbacks (ctx is a VehicleScriptContext, vehicle a VehicleWrapper):

function create(ctx, state, vehicle) { /* Before the first render: build textures, register callbacks */ }
function render(ctx, state, vehicle) { /* Every frame: read state, submit draws and sounds */ }
function dispose(ctx, state, vehicle) { /* On retirement: release textures */ }

Hiding the built-in destination sign

Vehicles built on the stock models can use hideDisplayParts (MTR 4) / hide_display_cube (MTR 3) to hide the bundled destination display cube and draw their own instead.

Vehicle data fetch modes

MTR 4 only synchronises nearby data, whilst vehicle scripts often want station names for the whole route. JCM's three levels (the dataFetchMode field):

ModeBehaviour
SKIPThe MTR 4 default. Requests nothing from the server and locally assembles a best-effort stop list—completeness not guaranteed. Enough for scripts that only look at speed, like 'ring a bell the moment the train moves'
ALLFetches the whole stop list first, then fetches station / route data one id at a time. Behaves like SKIP until it arrives; even with the stop list in hand, Stop.station / Stop.route may still be null—null-check them
MANDATORYSame as ALL, but the script does not start at all until all the data has arrived. The default for the MTR 3 format (old scripts expect data ready to use and cannot cope with null)

Eyecandy scripts

Attached to MTR eyecandy (Decoration Object) model entries: the script starts working when an eyecandy block using that model is rendered. Register with objects + objectScripts (the MTR 3 legacy format writes to eyecandy.json); isScriptControlled: true on the content entry hides the original model and hands the whole picture over to the script.

The three callbacks: ctx is an EyeCandyScriptContext, eyecandy an EyecandyWrapper.

Deprecated: the direct field-reading forms (eyecandy.translateX, eyecandy.prefabId and so on) still work.

Example: looped music that dims on right-click

Mount looped music with TickableSoundInstance.create(...) + setLoopable(true); within 5 seconds of a right-click setSoundVolume(0.25), restore 1.0 when the time is up, and stop in dispose—full code in the upstream sounds documentation.

Lift scripts

Attached to a lift car style (texture) entry; it takes effect once the player selects that style with the lift refresher. Register with lifts + liftScripts; isScriptControlled: true on the style entry hides the original model.

The three callbacks: ctx is a LiftScriptContext, lift a LiftWrapper.

LiftScriptContext (ctx)

getRenderManager(): RenderManager (base = the lift's base position + offset, rotating with the lift) · getSoundManager(): SoundManager (same base) · setDebugInfo(...).

PIDS scripts

A separate system

This system is mutually incompatible with PIDS Layout Editor / PIDS Modularization / PIDS JSON (EpicPuppy) and the information-screen customisation of the early MTR 4 test builds; the formats cannot be imported into one another—a higher barrier to entry, but it can do far more sophisticated layouts.

In the pids_images array of joban_custom_resources.json, a preset object carrying scriptFiles or scriptTexts becomes a script preset (scriptInput / scriptRateLimit mean the same as for the other kinds; Yanyang also accepts scriptLocations to mix in C++—see Mixed entries):

{
    "pids_images": [
        {
            "id": "pids_demo",
            "name": "Demo Scripted PIDS",
            "scriptFiles": ["jsblock:scripts/pids_demo.js"],
            "scriptInput": { "theme": "dark" },
            "scriptRateLimit": 0.75
        }
    ]
}

What you draw on a PIDS are polygons in the world, not a 2D canvas—elements may spill past the screen's edges, and clipping to the view is the script's own responsibility (when you genuinely need complex clipping / image processing, paint a GraphicsTexture first and mount it). Draw order is layering: later draws cover earlier ones; by default each draw advances a small step along z (0.0002) to prevent z-fighting, which can be switched off with ctx.setAutoZOrdering(false) in favour of manual zOrder() (with ctx.setZOrderStep(m) adjusting the step).

Dynamic textures on PIDS

A PIDS can mount a GraphicsTexture too: new GraphicsTexture(pids.width, pids.height) in create, paint and upload() in render, then Texture.create().texture(state.tex.identifier).size(pids.width, pids.height).draw(ctx), and close() in dispose—the fallback for when text layout lets you down, at the cost of performance and memory.

Don't need a script? A pids_images entry with only the JSON fields background / color / fonts / showWeather / showClock / hidePlatform / hideRow / topPadding / textOverflowMode and so on is a 'JSON preset'—enough for a simple facelift, and mutually exclusive with a script preset (the two cannot be combined in one entry).

DisplayHelper (the built-in multi-screen helper)

A ready-made solution for multi-screen vehicles: after include(Resources.id("mtrsteamloco:scripts/display_helper.js"))—

let slotCfg = {
    "version": 1,
    "texSize": [2048, 1024],
    "slots": [
        { "name": "lcd_north", "texArea": [0, 0, 2048, 274],
          "pos": [[[-0.59, 2.125, -1.75], [-0.755, 2.03, -1.75],
                   [-0.755, 2.03, -3.25], [-0.59, 2.125, -3.25]]],
          "offsets": [[0, 0, -5], [0, 0, 0], [0, 0, 5], [0, 0, 10]] }
    ]
};
let dhBase = new DisplayHelper(slotCfg);

function create(ctx, state, vehicle) {
    state.rl = new RateLimit(0.05);
    state.dh = dhBase.create();          // Instantiate and bind the texture
}
function render(ctx, state, vehicle) {
    if (state.rl.shouldUpdate()) {
        let g = state.dh.graphicsFor("lcd_north");  // The slot's canvas (auto-offset)
        // ... AWT drawing ...
        state.dh.upload();
    }
    for (let car of ctx.getMyCars())
        ctx.getCarRenderManager(car).drawModel(state.dh.model, null);  // Must be drawn every frame
}
function dispose(ctx, state, vehicle) {
    state.dh.close();
}
  • All slots share one large texSize texture; texArea picks the region each slot uses (x, y, w, h).
  • pos is a three-dimensional array: the four corner coordinates of each screen (top-left → bottom-left → bottom-right → top-right), in metres (divide Blockbench's 1/16 units by 16); the origin sits at the train's centre at floor height, with +X left / +Y up / +Z rear.
  • offsets duplicates screens showing the same content (a texture saver for runs of small screens above doors); graphicsFor(name) hands you the auto-offset canvas for a slot, graphics() the whole thing.
  • Put the upload inside the RateLimit and the model drawing outside it—the model must be submitted every frame.
