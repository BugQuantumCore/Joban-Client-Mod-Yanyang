四類腳本之基類、逐實例之狀態、生命週期之時序，暨線程與崩潰隔離之義。

四類腳本

納 <mtr/script.hpp>，承所應之基類，以註冊宏導出。基類模板之參數，即逐實例狀態之型：

資源基類註冊宏數據包裝器
車輛mtr::VehicleScript<State>MTR_REGISTER_VEHICLE_SCRIPTmtr::Vehicle
PIDSmtr::PidsScript<State>MTR_REGISTER_PIDS_SCRIPTmtr::Pids
電梯mtr::LiftScript<State>MTR_REGISTER_LIFT_SCRIPTmtr::Lift
裝飾mtr::EyecandyScript<State>MTR_REGISTER_EYECANDY_SCRIPTmtr::EyeCandy

一車輛腳本之骨架（餘三類惟易基類與參數之型）：

#include <mtr/script.hpp>

struct MyVehicleState {
    mtr::CycleTracker dest{"KOWLOON|TSUEN WAN"};   // 君自定之任意 C++ 類型
    mtr::Api::Object tracker;                        // Java 物件之柄
    std::unique_ptr<mtr::GraphicsTexture> lcd;    // 所持之資源
};

struct MyVehicleScript : mtr::VehicleScript<MyVehicleState> {
    static constexpr auto ID = "demo:vehicle";

    void create(mtr::VehicleContext& ctx, MyVehicleState& state,
                const mtr::Vehicle& vehicle) override {
        // 首幀之前一呼：造資源、註回呼
    }

    void render(mtr::VehicleContext& ctx, MyVehicleState& state,
                const mtr::Vehicle& vehicle) override {
        // 每幀一呼：讀快照、書繪製記錄
    }

    void dispose(mtr::VehicleContext& ctx, MyVehicleState& state,
                 const mtr::Vehicle& vehicle) override {
        // 實例銷毀前一呼：釋放資源
    }
};

MTR_REGISTER_VEHICLE_SCRIPT(MyVehicleScript)
  • ID 者，腳本命名空間之 id（如 demo:vehicle），必與資源包 minecraft_custom_resources.json 中宣告條目之 id 相合。
  • 三生命週期函數皆可省 override（基類有空虛實現），參數之簽名則固。
  • 一翻譯單元註一腳本；腳本多者，分為多模塊庫。

State：逐實例之狀態

每腳本實例（每車、每 PIDS 方塊實體……）各有獨立之 State 一塊，由宿主分配而構造：

  • 宿主按 mtrStateSize()（註冊宏自 sizeof(State) 所生）配狀態塊，首用之前經 mtrInit() 以 placement-new 構之——勿以為零填充之記憶體可用（std::string 等非平凡之型施於零記憶體，乃未定義之行）。
  • 狀態塊之內容跨幀恆存：紋理、模型之柄、回呼、緩存，皆置諸此。
  • 腳本類之成員（君於 MyVehicleScript 所書之欄）則為該模塊諸實例所共——惟置唯讀常數與全域配置。
  • dispose 既返，狀態隨即析構；實例自客戶端而沒，約五秒而退休，資源包重載（F3+T）之時則盡毀之。
要訣

後臺回呼之物（mtr::Api::Callback）必存於 State 以至於銷毀——Java 側或於任意之時呼之。

生命週期之時序

分配＋構造

宿主為實例配狀態塊而呼 mtrInit() → State() 構焉。

create

實例首度渲染之前一呼。create 期間所呈之繪製記錄，必留至首幀 render 而復用——一次性靜態之內容（形狀、常駐貼圖）置諸此，render 惟繪動態之部。資源之取、Api 之呼、回呼之註，亦宜在焉。

render（每幀）

讀快照 → 運算 → 以繪製記錄書於幀競技場。快照與包裝器惟本次呼叫之內有效；宿主於 render 既返，即讀其輸出而收其幀。實例不可見之時，render 不為所呼，而狀態保其熱。

dispose

實例退休或重載之時呼之。於此閉所持之紋理 / 模型等資源；State 之析構隨之。縱 dispose 擲異常，狀態亦必安然析構。

與 JS 相應

此 create / render / dispose ＋ 逐實例 state 之制，即 JCM 為 JS 腳本所設之模型（每 ScriptInstance 一 state 物件）原生之映；遷 JS 腳本之時，邏輯得逐段對譯。

線程模型

  • 宿主為每模塊於單一後臺線程之上串行呼其全部生命週期函數（映 JCM 於 JS 腳本逐腳本單線程執行之器）——同一實例之 create / render / dispose 永不並發。
  • 然 render 與非同步回呼得並發（如 BackgroundWorker 所呈之任務，此刻方行於他線程）：同步共享可變之狀態，腳本自任其責。
  • 資源包重載，必先止回呼、俟方行呼叫之返，而後毀狀態、卸程式碼。

崩潰隔離

註冊宏裹每一導出函數於崩潰圍欄（crash_guard.hpp）：

  • 段錯誤（segmentation fault）等硬體之疾 → 惟禁該模塊，遊戲行程行如故；latest.log 留 native script faulted … module disabled 一行。
  • 未獲之 C++ 異常亦為圍欄所截——然請自 try/catch，以保語義之明。
  • POSIX 訊號不為 longjmp 式之「復」：越訊號處理器之跳，危於崩潰本身，故模塊逕下線者，蓋刻意之設也。

返回之碼

mtrCreate / mtrRender / mtrDispose 所返其義
0成功
-1入參為空
-2ABI 版本不合（宿主與模塊商議不成）
-3資源類型不合（如車輛模塊被當 PIDS 而呼）

此諸返回之碼，SDK 所生也，尋常腳本之碼無須掛懷；若君方撰自定義宿主 / 測試驅動，按上表解之可也（詳見 C ABI 與宿主服務）。

繼之：數據快照 —— render 之時所可讀者何；繪事與畫布 —— 何以繪而出之。
