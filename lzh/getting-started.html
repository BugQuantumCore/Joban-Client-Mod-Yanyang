先決之件

工具版本釋義
C++ 編譯器C++17MSVC（Windows）/ GCC / Clang 任擇其一
CMake≥ 3.16所薦，然非硬性之求——SDK 純為頭文件
JDK可省惟行 SDK 自帶 JVM 集成測試時所需
要訣

SDK 悉以頭文件供之（native/include/mtr/），無毫釐預編譯庫之依賴；以君所熟之構建系統，徑納 include/ 於包含路徑即可。

取 SDK

SDK 隨每 Release 刊為 jcm-native-sdk-<版本>.zip（見 GitHub Releases 之附件），其內即倉庫 native/ 目錄之源碼：

jcm-native-sdk-2.3.0-beta-2.yanyang.7/
├── include/mtr/          # SDK 諸頭文件盡在（script.hpp 為總門）
│   ├── mtr_native.h      # C ABI：導出函數、快照、繪製記錄、宿主服務
│   ├── script.hpp        # 腳本基類＋註冊宏（惟 #include 此一足矣）
│   ├── vehicle.hpp  pids.hpp  lift.hpp  eyecandy.hpp
│   ├── gfx.hpp  gfx2d.hpp  font5x7.hpp  text.hpp  matrices.hpp
│   ├── api.hpp           # mtr::Api（Java API 之全訪）
│   └── crash_guard.hpp ...
├── examples/             # 最小示例模塊凡三
├── bench/                # 測試與器具
└── CMakeLists.txt

立模塊工程

至簡之法：解 SDK 於君之資源包工程，徑於其 CMakeLists.txt 之末追加己之目標——SDK 已將諸平臺鏈結之細務（Windows 無前綴 .dll、macOS .dylib 與 -undefined dynamic_lookup、Android 16 KB 頁對齊）封為 mtr_add_script() 一函：

# 追加於 SDK native/CMakeLists.txt 之末
mtr_add_script(my_pids src/my_pids.cpp)

若欲自立工程，下方即與彼函數等價之全模板：

cmake_minimum_required(VERSION 3.16)
project(my_native_scripts LANGUAGES CXX)

set(CMAKE_CXX_STANDARD 17)
set(CMAKE_CXX_STANDARD_REQUIRED ON)

# SDK 頭文件路徑（指往解壓所得 SDK 之 include 目錄）
add_library(mtr_script_sdk INTERFACE)
target_include_directories(mtr_script_sdk INTERFACE path/to/sdk/include)

function(mtr_add_script name)          # 與 SDK 同式之模塊目標函數
  add_library(${name} MODULE ${ARGN})
  target_link_libraries(${name} PRIVATE mtr_script_sdk)
  set_target_properties(${name} PROPERTIES CXX_VISIBILITY_PRESET hidden)
  if(WIN32)
    set_target_properties(${name} PROPERTIES PREFIX "" SUFFIX ".dll")
  elseif(APPLE)
    set_target_properties(${name} PROPERTIES PREFIX "lib" SUFFIX ".dylib")
    target_link_options(${name} PRIVATE "-Wl,-undefined,dynamic_lookup")
  elseif(ANDROID)
    target_link_options(${name} PRIVATE "-Wl,-z,max-page-size=16384")
  endif()
endfunction()

mtr_add_script(my_pids src/my_pids.cpp)
按語

腳本為 MODULE 庫（不鏈任何 SDK 二進位之物），預設符號隱藏，惟導出 ABI 所求之七個 mtr* 函數（由 script.hpp 之註冊宏成之）。C++17 乃最低之標準。

第一模塊

一至小之 PIDS 到站顯示模塊——完備、可編譯、可徑入遊戲：

#include <mtr/script.hpp>

struct ArrivalState {};                    // 逐實例恆存之狀態（本例為空）

struct ArrivalDisplay : mtr::PidsScript<ArrivalState> {
    static constexpr auto ID = "example:arrivals";   // 須與資源包之宣告相符

    void render(mtr::PidsContext& ctx, ArrivalState&,
                const mtr::Pids& pids) override {
        for (int row = 0; row < pids.rows(); row++) {
            if (pids.is_row_hidden(row)) continue;

            std::string text = pids.get_custom_message(row).str();
            if (text.empty() && row < pids.arrivals().size())
                text = pids.arrivals().at(row).destination().str();

            if (!text.empty())
                mtr::Text::create()
                    .text(text.c_str())
                    .pos(2, row * 10.0 + 2)
                    .size(pids.width() - 4, 9)
                    .draw(ctx);
        }
    }
};

MTR_REGISTER_PIDS_SCRIPT(ArrivalDisplay)

其要曰：

  • 基類定腳本之屬：PidsScript / VehicleScript / LiftScript / EyecandyScript，模板參數即逐實例狀態之型。
  • 生命週期與 JS 無異：create / render / dispose 三虛函數按所需而 override（皆可省）。
  • 註冊宏敷展全部 ABI 導出，一翻譯單元惟註一腳本。

更多示例見 SDK 之 examples/：車輛 / 電梯 / 裝飾三類各有至小之樣。

編譯

cmake -S native -B native/build -DCMAKE_BUILD_TYPE=Release
cmake --build native/build --config Release --parallel 4
ctest --test-dir native/build -C Release --output-on-failure   # 可省：行 SDK 自帶之測試
目標平臺產物釋義
Windows x64my_pids.dllMSVC，/utf-8 已由 SDK 工程預設
Linux x64 / ARM64libmy_pids.soGCC / Clang
macOS x64 / arm64libmy_pids.dylib以 -DCMAKE_OSX_ARCHITECTURES=arm64（或 x86_64）擇架構，-DCMAKE_OSX_DEPLOYMENT_TARGET=11.0
Android arm64libmy_pids.soNDK 工具鏈交叉編譯，API 21+；16 KB 頁對齊已由工程模板處之
iOS / iPadOS arm64libmy_pids.dylibMach-O 交叉編譯，無須簽章（側載時重簽之）
要訣

資源包內之庫，按副檔名繫乎平臺（.dll → Windows、.so → Linux/Android、.dylib → macOS/iOS），目錄之詳規見下節。

納諸資源包

目錄之布局

置諸平臺編譯之產物於資源包 natives/<platform>/ 之目錄：

my_pack/
├── natives/
│   ├── windows-x64/my_pids.dll
│   ├── linux-x64/libmy_pids.so
│   ├── linux-arm64/libmy_pids.so
│   ├── macos-x64/libmy_pids.dylib
│   ├── macos-arm64/libmy_pids.dylib
│   ├── android-arm64/libmy_pids.so
│   └── ios-arm64/libmy_pids.dylib
└── ...（貼圖、模型等其餘資源）

宣之於 minecraft_custom_resources.json

無須 language 欄——模組按 scriptLocations 中每條目之特徵自判其語，JS 與 C++ 於同一條目得混用任意之數：

"pidsScripts": [{
    "id": "example:arrivals",
    "scriptLocations": [
        "mtr:my_pack/natives/my_pids"
    ]
}]

條目解析之規：

scriptLocations 條目所判
…/main.js（不辨大小寫）JavaScript
mtr:my_pack/natives/my_pids（無副檔名）C++ 平臺無關之 stem → 諸平臺自析為 natives/linux-x64/libmy_pids.so、natives/windows-x64/my_pids.dll、natives/macos-arm64/libmy_pids.dylib 等；ARM64 Linux 之境自動益以 ios-arm64 / android-arm64 候選
…/libfoo.so / ….dll / ….dylibC++ 完整路徑（繫於該副檔名所應之平臺，餘臺跳過）
{"windows": …, "linux": …, "macos": …}C++ 按平臺映射之表；許 macos-arm64 等精確之鍵（精確之鍵先於通用之鍵）
  • 四類腳本同其規：vehicleScripts / pidsScripts（暨 PIDS 預設之 scriptLocations）/ 電梯 / 裝飾，皆許上述混雜之宣告。
  • 舊格相容："language": "cpp" 加 nativeLibrary / nativeLibraries 之舊宣告依然有效，亦得與 .js 混用；"language": "javascript" 可強使整條按 JS 解之。
  • JS 欄如常：prependExpressions / input / dataFetchMode 等欄之義不變，C++ 側經 api.input() 讀 input。
慎之

腳本模塊（君所編之 .dll/.so/.dylib）屬乎資源包，納諸 natives/<platform>/；模組 jar 自帶之 assets/jcm/natives/ 惟有原生橋，二者慎勿相混。遊戲惟載當前作業系統所應平臺之庫。

驗於遊戲之中

  1. 安 JCM Yanyang 與 MTR，置資源包於 resourcepacks/ 而啟之（或以內建資源隨存檔散之）。
  2. 置所應之方塊（如 PIDS），於配置中擇君之腳本 / 使宣告條目生效。
  3. 啟 logs/latest.log，索 native script——模組載入之際，必印模塊 census 之摘要（模塊之數、腳本之類、傳輸通道等）。見君之 example:arrivals，則載入成矣。
  4. 既改庫文件，按 F3+T 重載資源包，即可重載 C++ 腳本（或用模組所供「重載全部 MTR 腳本」之快捷鍵），無須重啟遊戲。
切記

必用 Release 版 jar 或 Complete Build 之產物。push/PR 之速成 CI 產物不含原生橋，日誌必示 native bridge unavailable，諸 C++ 腳本盡被略過——此非君模塊之過。
