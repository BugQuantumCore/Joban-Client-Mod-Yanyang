數據快照

每幀一遭，宿主搬運之唯讀數據也。諸訪問器所為，皆尋常記憶體之讀——零 JNI，零反射，零裝箱。

快照之機

每幀方始，宿主以此實例之數據一舉搬運，為一 POD 快照：定長之首，變長之陣列池，UTF-8 字串之池，三者具焉；連狀態塊之指針，併傳於 mtrRender。SDK 之具型包裝器（mtr::Vehicle、mtr::Pids、mtr::Lift、mtr::EyeCandy）居此記憶體之上，供與 JS Wrapper 同名之訪問器：

  • 字串以 mtr::StrView（data＋len）而返；.str() 則轉為 std::string，.empty() 則判其虛實。視圖惟本次 render 一呼之內為效。
  • 常式之列，索引越界，則擲 std::out_of_range（與 Java 端 IndexOutOfBounds 同其義也）。
  • 快照之指針與包裝器，慎勿跨幀而存之。
所覆之範

快照所覆者，高頻讀取之欄而已。數據之不在快照者（網路也，檔案也，渲染管理器之深介面也），則經 mtr::Api 而訪之——彼固低頻之通道，勿用於熱路徑也。

Vehicle（車輛）

術語：MTR 三代之 train → MTR 四代之 vehicle

MTR 四代之制，載具統名曰 vehicle（資源包宣告之鍵 vehicleScripts，Java 側則 VehicleWrapper 是也），故本 SDK 數據包裝之類，名之曰 mtr::Vehicle。前代 SDK 嘗循 MTR 三代之舊，名之曰 mtr::Train；今舊名猶存，為源碼相容之別名——二名並可編譯，所行全同。

按：mtr::Vehicle 之名已入倉庫 SDK 之原碼，將隨次版之 zip 而布；君所用若 2.3.0-1.0.2 或更早之 SDK zip，則請以 mtr::Train 名之（新 SDK 之中，二名並可編譯）。

交通之模式與類型

二者相補之口徑也；與 JS 側 getTransportMode() / getTransportType() 所返之值全同，故跨語言之腳本，得共享布局之邏輯：

  • 模式（mtr::TransportMode 枚舉）：UNKNOWN / TRAIN / BOAT / CABLE_CAR / AIRPLANE，覆基礎載具凡四。
  • 類型（字串 id，mtr::transport_type 常數）：基礎模式小寫之名（"train"、"boat"、"cable_car"、"airplane"），益以 MAGIC MTR Addon 所擴線路之類 train_normal / train_light_rail / train_high_speed / train_metro / train_bus / train_tram / train_sbahn；其不可解者，則為 "unknown"，或空視圖（舊伺服器之數據也）。
if (vehicle.getTransportType() == mtr::transport_type::TRAIN_METRO) { /* ... */ }

for (int i = 0; i < stop.interchange_count(); i++) {
    mtr::Stop::Interchange ic = stop.interchange(i);
    if (ic.getTransportType() == mtr::transport_type::TRAIN_HIGH_SPEED) { /* ... */ }
}
數據所自

MAGIC 諸類之所自：客戶端裝其 addon 者，自本地之配置而解；伺服器裝而客戶端未裝者，經同步數據集而下；舊伺服器不下線路元數據者，返空 / UNKNOWN——裝本模組之伺服器，則供遠端車站以完備之元數據。

天氣（ABI 15）

五類快照（車輛 / PIDS / 屏蔽之門 / 電梯 / 裝飾）一律攜客戶端世界天氣之狀——JS 與 C++ 所返全同，兩側之腳本得共享布局之邏輯（雨天「地滑慎行」之示、雷雨服務之告之屬）：

if (psd.getWeather() == mtr::weather::RAIN) drawWetFloorNotice();
switch (vehicle.weather()) {
    case mtr::Weather::RAIN:    drawRainOverlay(); break;
    case mtr::Weather::THUNDER: drawThunderServiceNotice(); break;
    default: break;
}
  • 取之之法：weather() 返 mtr::Weather（CLEAR / RAIN / THUNDER）；getWeather() 返字串之 id（"clear" / "rain" / "thunder"，與 mtr::weather 常數相較——循 transport_type / door_direction 命名之例）。
  • 其判與 MTR 自帶天氣 PIDS 之件無異：isThundering() 先於 isRaining()；無客戶端世界，則恆 clear。
  • 布局：車輛 weather @165（原 _pad1[0]）、PIDS @63（原 _pad0）、電梯 @127（原 _pad0）、裝飾 @67（原 _pad0）；JcmPsdSnapshot 者，惟一無空位元組之快照也——首部之長 128 → 136，天氣之位元組居 128（諸池之偏，皆自 blob 而起；ABI 12–14 之模塊惟讀偏 < 128，不受其擾）。四處皆疇昔書零而未嘗一讀之填補，老模塊無恙也。
  • JS 之側，同名之法徑呼：pids.getWeather() / vehicle.getWeather() / psd.getWeather() / lift.getWeather() / eyecandy.getWeather()（所返同一字串之 id）。

道口 / 售檢票機 / 廣播（ABI 16）

三類方塊腳本錨於方速（FangSu）相應之方塊，由客戶端本地之繫而驅（持「屏蔽門腳本編輯器」右擊方塊以擇腳本；繫存於 config/jcm/native_block_scripts.json，按維度而群——三類腳本皆純視聽之疊，不改世界之狀）。基類與註冊宏，見 腳本體例；宣告之鍵曰 levelCrossingScripts / fareMachineScripts / announcementScripts，與他類同一宣告之規。無方速，則三類皆空轉也。

LevelCrossing（道口）

快照 JcmLevelCrossingSnapshot（72 位元組）攜幾何之概與將至車列之池；欄木之動，腳本之狀自驅之，宿主惟予其目標之狀而已：

訪問器釋義
pos_x() / pos_y() / pos_z()所繫方塊世界之坐標
track_yaw_degrees()主軌之向 yaw 角（方速幾何所採；-1 者未知也）——欄木對齊之用
warningState() / isWarning()宿主所推警示之狀：IDLE / WARNING（有一車入警戒之徑矣）
barrierTarget() / barrier_closed()宿主所推欄木之的：OPEN / CLOSED（警示之期則下）——腳本以其欄木之動趨此的而進
approaches()CrossingApproachList：將至車列之池（見下）
weather() / getWeather() · fangsu_present() · game_time_millis()天氣（同 ABI 15）/ 所繫方塊誠方速道口否 / 時鐘

每 CrossingApproach（64 位元組）：

訪問器釋義
vehicle_id() / route_id()車輛 / 線路之 id（64 位）
distance_blocks() / speed_kmh() / seconds_to_arrival()距（格）/ 速 / 至站秒數之估
car_count() / destination() / arrival_millis() / arrived()車廂之數 / 終點 / 既正到站之刻（0 者未知也）/ 已至否

繪製上下文 LevelCrossingContext（回放之途，與裝飾同一渲染管理器）：draw_model(model, matrices)，暨帶式之變體 draw_model(model, matrices, tint_argb, emissive, translucent)（警示之燈 emissive、燈罩之璃 translucent——見 繪事與畫布）、play_sound(sound, volume, pitch)（定位之音，出於方塊之處）。

FareMachine（售檢票機）

快照 JcmFareMachineSnapshot（96 位元組）——小屏動態內容（票價、餘額之示、擁擠之度）之數據面也：

訪問器釋義
machineType()BARRIER（閘機，錨方速 ticket_barrier）/ TICKET_MACHINE（售票機，錨 ticket_machine）
open() / door_value()閘機之啟闔（方速 isOpen extraConfig）/ 翼門動之值 0（啟）..1（闔）——循方速 200ms 啟 / 500+200ms 闔之時序，由啟闔之沿而推；售票機恆 0
exit_side() / facing()出站之側（區域票價之閘）/ 朝向（MC Direction 0..5）
fareType() / fare_value()ZONE_BASED / FLAT；一口之票價（區域之票，經快照站名與 JS 側票價之表而解）
player_balance()客戶端玩家 mtr_balance 計分板之值（-1 者未知也）——「餘額之示」屏所顯之數
station_name() / arrivals()所屬車站（未解者空）/ 最近站台到站之池（FareArrival 具 Pids Arrival 諸訪問器之全，加 isExpress() / isHiddenRoute()）
weather() / getWeather() · fangsu_present() · pos_x/y/z() · game_time_millis()同上

繪製上下文 FareMachineContext：draw_model(model, matrices[, tint, emissive, translucent])（屏之發光 emissive、璃罩 translucent＋alpha 染色）、play_sound(...)。

Announcement（報站廣播）

快照 JcmAnnouncementSnapshot（88 位元組）——統一音頻調度之 API 也；「本班既播」之去重，腳本之狀（departure_key()）司之：

訪問器釋義
lead_seconds() / all_stops()提前廣播之秒數（所餘既入其窗即發）/ 非站站停之班亦播否
template_id() / variant()模板 / 變體之識（未設者空）——不待自攜配置，即可易其播報之風
binding_count() / binding_route(i) / binding_platform(i)所繫（線路， 站台）之對（≤ 32；方速之式中，(0, 0) 謂範圍內諸站台——宿主如原本而轉之）
arrivals()AnnouncementArrivalList：諸所繫站台到站之池（按 departure 去重，按到站之刻而序）；每條含 arrival_time() / departure_time() / route_id() / destination() / route_name() / seconds_until_arrival() / isExpress() / isHiddenRoute() / realtime() / terminating() / car_count()
weather() / getWeather() · fangsu_present() · pos_x/y/z() · game_time_millis()同上

音頻經統一聲音記錄而回放（與 PIDS 之 ScriptSoundManager 同其義——音量 / 音高 / 距離之裁，一皆相同）：ctx.play_sound(id, volume, pitch)（定位之音，出揚聲器方塊之處，範圍內諸玩家皆聞）、ctx.play_local_sound(id, volume, pitch)（乘者專享之途）。例（SDK examples/ 之風）：

struct State { std::unordered_set<int64_t> announced; };
void render(mtr::AnnouncementContext& ctx, State& s, const mtr::Announcement& an) override {
    auto arrivals = an.arrivals();
    for (int i = 0; i < arrivals.size(); i++) {
        const double remain = (arrivals[i].arrival_time() - an.game_time_millis()) / 1000.0;
        if (remain > 0 && remain <= an.lead_seconds()
            && s.announced.insert(arrivals[i].departure_key()).second) {
            ctx.play_sound("demo:chime", 1.0f, 1.0f);
        }
    }
}
驅之之節

方塊腳本之驅，與車輛腳本同掛逐幀注入之點（亦跳光影陰影之段）：原生之驅約 12 Hz（反射之探 / 車輛之掃 / 到站之詢，皆為之節），繪製之回放則逐幀——捕與回放之分，同 PIDS / PSD 之律，模型不閃。資源之解，循既有 mtr_custom_resources.json 宣告之管道（三鍵皆純 native 之宣告）。

器用之型

<mtr/util.hpp> 供輪播與狀態追跡之器具，於熱路徑甚友善（零分配）：

// "A|B|C" 每 40 tick 更迭一段，切視圖惟算偏移
mtr::CycleTracker dest{"KOWLOON|TSUEN WAN"};
StrView current = dest.value(vehicle.in_game_time());
成員釋義
CycleTracker(packed, interval_ticks=40)構輪播（映 TextUtil.cycleString）
value(game_tick) / value_str(game_tick)當前活躍之段（視圖 / 字串）
interval() / part_count()更迭之隔與段數
StrView{data, len} 字串之視圖：.str()、.empty()，可比之以 ==

狀態機之追跡，則有 mtr::StateTracker<T> 焉（映上游 StateTrackerJS；時鐘顯傳——快照之 game_time_millis()，天然之準也）：以其欄納諸 State，render 之際，一斷其遷而已：

struct State {
    mtr::StateTracker<Phase> phase;   // 跨幀常存
};

// render 之中：
if (s.phase.set_state(next, vehicle.game_time_millis())) {
    // 得 true —— 初入此態之幀也（上游 prerelease.2 新義）
}
double staying = s.phase.state_now_duration(vehicle.game_time_millis());
if (s.phase.changed_from_to(PHASE_IDLE, PHASE_ARRIVING)) { /* 演進場之動畫 */ }
成員釋義
set_state(value, now_ms)更其狀態；所返者，初入此態之幀否（上游 v2.3.0-prerelease.2 起 setState 返布林）
state_now() / state_last() / state_now_first()今態 / 前態；初幀否
state_now_duration(now_ms)今態所歷之毫秒
changed_to(state) / changed_from_to(old, new)此幀入某態否 / 自某態而遷否

繼之：繪事與畫布 —— 取此數據而繪之。
