Data snapshots

Read-only data marshaled by the host once per frame. Every accessor is a plain memory read — zero JNI, zero reflection, zero boxing.

How snapshots work

At the start of each frame, the host marshals the instance's data in one shot into a POD snapshot (fixed-length header + variable-length array pools + a UTF-8 string pool) and passes it, together with the state block pointer, to mtrRender. The SDK's typed wrappers (mtr::Vehicle, mtr::Pids, mtr::Lift, mtr::EyeCandy) provide same-named accessors over that memory as the JS Wrappers:

  • Strings come back as mtr::StrView (data + len); call .str() to convert to std::string and .empty() to test for empty; views are valid only within the current render call.
  • Out-of-range indexes in ordinary lists throw std::out_of_range (matching the Java side's IndexOutOfBounds semantics).
  • Do not keep snapshot pointers or wrappers across frames.
Coverage

Snapshots cover the fields read at high frequency. Data that is not in the snapshot (networking, files, deep interfaces of the render managers, etc.) is reached through mtr::Api — that is the low-frequency channel; keep it off the hot path.

Vehicle

Terminology: MTR 3's train → MTR 4's vehicle

MTR 4 uniformly calls these vehicles (the resource pack declaration key is vehicleScripts, the Java side is VehicleWrapper), so this SDK's data wrapper class is named mtr::Vehicle. Earlier SDK releases named it mtr::Train after the MTR 3 convention; that name is now kept as a source-compatible alias — both spellings compile and behave identically.

Note: the mtr::Vehicle name is in the repository's SDK sources and ships with the next release's zip; if your project uses the 2.3.0-beta-2.yanyang.7 (or earlier) SDK zip, refer to this class as mtr::Train (both spellings compile against the new SDK).

Transport modes and types

Two complementary views: the JS-side getTransportMode() / getTransportType() return exactly the same values, so scripts across languages can share layout logic:

  • Mode (the mtr::TransportMode enum): UNKNOWN / TRAIN / BOAT / CABLE_CAR / AIRPLANE, covering the four basic vehicles.
  • Type (a string id, the mtr::transport_type constants): the lowercase names of the basic modes ("train", "boat", "cable_car", "airplane") plus the extended route types of the MAGIC MTR Addon — train_normal / train_light_rail / train_high_speed / train_metro / train_bus / train_tram / train_sbahn; unresolvable values come back as "unknown" or an empty view (older server data).
if (vehicle.getTransportType() == mtr::transport_type::TRAIN_METRO) { /* ... */ }

for (int i = 0; i < stop.interchange_count(); i++) {
    mtr::Stop::Interchange ic = stop.interchange(i);
    if (ic.getTransportType() == mtr::transport_type::TRAIN_HIGH_SPEED) { /* ... */ }
}
Where the data comes from

MAGIC types resolve from local configuration when the client has the addon installed; when the server has it but the client doesn't, they arrive through the synchronized data set; older servers that don't send route metadata yield empty / UNKNOWN — servers running this mod can supply full metadata for remote stations.

PsdStation (the station record, ABI 13)

JcmPsdSnapshot.station_offset (byte offset 124; -1 = no station — the field was padding in ABI 12) points at the 96-byte JcmPsdStation record — the same data the JS psd.stop() object exposes:

PsdStation and its nested station accessors return absent objects, empty strings or defaults for invalid indices or records instead of throwing index exceptions. When constructing a snapshot outside the host, pass the actual buffer size to mtr::Psd(snapshot, byteLength). The compatible pointer-only constructor requires a fully readable header and its declared backing buffer; a raw pointer cannot reveal the allocation size.

Weather (ABI 15)

All five snapshots (vehicle / PIDS / PSD / lift / eyecandy) uniformly carry the client world's weather state — JS and C++ return exactly the same values, so scripts on both sides can share layout logic (a "mind the wet floor" notice row on rainy days, thunderstorm service notices, and so on):

if (psd.getWeather() == mtr::weather::RAIN) drawWetFloorNotice();
switch (vehicle.weather()) {
    case mtr::Weather::RAIN:    drawRainOverlay(); break;
    case mtr::Weather::THUNDER: drawThunderServiceNotice(); break;
    default: break;
}
  • Values: weather() returns mtr::Weather (CLEAR / RAIN / THUNDER); getWeather() returns the string id ("clear" / "rain" / "thunder", compared against the mtr::weather constants — the same naming convention as transport_type / door_direction).
  • The verdict matches MTR's own weather PIDS component: isThundering() takes precedence over isRaining(); without a client world it is always clear.
  • Layout: vehicle weather @165 (the former _pad1[0]), PIDS @63 (the former _pad0), lift @127 (the former _pad0), eyecandy @67 (the former _pad0); JcmPsdSnapshot is the only snapshot without a spare byte — its header length grows 128 → 136 with the weather byte at 128 (all pool offsets are relative to the blob; ABI 12–14 modules only read offsets < 128 and are unaffected). All four fields were previously padding that was written as zero and never read, so older modules are unaffected.
  • The JS side calls the same-named methods directly: pids.getWeather() / vehicle.getWeather() / psd.getWeather() / lift.getWeather() / eyecandy.getWeather() (returning the same string ids).

Level crossings / fare machines / announcements (ABI 16)

The three block script kinds anchor to the matching FangSu blocks and are driven through client-local bindings (right-click the block with the PSD script editor to choose a script; bindings live in config/jcm/native_block_scripts.json, grouped by dimension — all three script kinds are purely visual/audio overlays and never modify world state). Base classes and registration macros are in Script model; the declaration keys are levelCrossingScripts / fareMachineScripts / announcementScripts, following the same declaration rules as the other kinds. Without FangSu all three idle completely.

Audio is replayed through the unified sound records (the same semantics as the PIDS ScriptSoundManager — identical volume / pitch / distance culling): ctx.play_sound(id, volume, pitch) (a positioned sound at the speaker block, audible to every player in range) and ctx.play_local_sound(id, volume, pitch) (the riding-players-only channel). An example (in the SDK examples/ style):

struct State { std::unordered_set<int64_t> announced; };
void render(mtr::AnnouncementContext& ctx, State& s, const mtr::Announcement& an) override {
    auto arrivals = an.arrivals();
    for (int i = 0; i < arrivals.size(); i++) {
        const double remain = (arrivals[i].arrival_time() - an.game_time_millis()) / 1000.0;
        if (remain > 0 && remain <= an.lead_seconds()
            && s.announced.insert(arrivals[i].departure_key()).second) {
            ctx.play_sound("demo:chime", 1.0f, 1.0f);
        }
    }
}
Drive cadence

The block script driver hooks the same per-frame injection point as vehicle scripts (likewise skipping the shader shadow phase): the native drive runs at about 12 Hz (throttling the reflection probes / vehicle scans / arrival queries) while draw replay happens every frame — the same capture-replay discipline as PIDS/PSD, so models never flicker. Resource resolution goes through the existing mtr_custom_resources.json declaration pipeline (all three keys are pure native declarations).
