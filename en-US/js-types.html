Vehicle scripts

A "vehicle" in MTR 4 is a single car model entry; players freely combine cars into trains in the siding screen. A script binds to neither a single car nor a whole train, but to a script entry: vehicle entries reference it via scriptId, and multiple vehicles can reuse the same script — mixed consists, performance, and NTE compatibility all at once.

The three callbacks (ctx is a VehicleScriptContext, vehicle is a VehicleWrapper):

function create(ctx, state, vehicle) { /* Before the first render: set up textures, register callbacks */ }
function render(ctx, state, vehicle) { /* Every frame: read state, submit draws and sounds */ }
function dispose(ctx, state, vehicle) { /* On exit: release textures */ }

Hiding the stock destination display

Vehicles built on the stock models can set hideDisplayParts (MTR 4) / hide_display_cube (MTR 3) to hide the built-in destination display blocks and draw their own in the script instead.

Vehicle data fetch modes

MTR 4 only syncs nearby data, while vehicle scripts often want station names for the whole route. JCM's three-tier model (the dataFetchMode field):

ModeBehavior
SKIPThe MTR 4 default. Requests nothing from the server and pieces together a best-effort stop list locally — completeness not guaranteed. Enough for scripts that only look at speed, like "ding as soon as the train moves"
ALLFetches the full stop list first, then fetches the station / route data for each id in it. Behaves like SKIP until that arrives; even with the stop list in hand, Stop.station / Stop.route can still be null — null-check
MANDATORYLike ALL, but the script doesn't start at all until all data has arrived. The default for the MTR 3 format (old scripts assume data is ready on arrival and can't tolerate null)

Decoration object scripts

Attaches to an MTR decoration object model entry: the script starts working when a decoration object block using that model from the resource pack is rendered. Register with objects + objectScripts (the MTR 3 legacy format writes these in eyecandy.json); setting isScriptControlled: true on the content entry hides the original model and hands the visuals entirely to the script.

The three callbacks: ctx is an EyeCandyScriptContext, eyecandy is an EyecandyWrapper.

EyeCandyScriptContext (ctx)

MemberDescription
getRenderManager(): RenderManagerThe base is the block position + the GUI offset, including the GUI rotation
getSoundManager(): SoundManagerThe base is the block position; there's also the convenience ctx.playSound(id, volume, pitch) to play right at the block
drawModel(model, matrices?)Draws a model (accepts a DynamicModelHolder too) — equivalent to getRenderManager().drawModel(...)
events(): EyecandyEventsEvent access: right-click events().onBlockUse.occurred() → handle it → confirm with events().handled(); the event detail .detail().player() gives the acting PlayerEntity (right-clicks while holding a brush don't count)
setOutlineShape(shape) / setCollisionShape(shape)Custom outline / collision box (VoxelShape); no effect while wielding the brush
setDebugInfo(...)Same as the other types

EyecandyWrapper (eyecandy)

getModelId(): String (the current model entry's id) · getTranslateX/Y/Z(): float (the GUI offset, in meters) · getRotateX/Y/Z(): float (the GUI rotation, in radians) · pos(): Vector3f (block + offset) · blockPos(): Vector3f · facing(): Direction · facingAngle(): double (the facing angle) · isCrosshairTarget(): boolean (the crosshair is on it — handy for tooltips) · getFullBrightness(): boolean · redstoneLevel(): int (0–15).

Deprecated: the direct field-reading forms (eyecandy.translateX, eyecandy.prefabId, and so on) still work.

Example: looping music that dims on right-click

Attach looping music with TickableSoundInstance.create(...) + setLoopable(true), drop to setSoundVolume(0.25) within 5 seconds of a right-click, restore 1.0 when time is up, and stop in dispose — full code in the upstream sounds documentation.

Lift scripts

Attaches to a lift car style (texture) entry and takes effect once the player selects that style with the lift refresher. Register with lifts + liftScripts; isScriptControlled: true on the style entry hides the original model.

The three callbacks: ctx is a LiftScriptContext, lift is a LiftWrapper.

LiftScriptContext (ctx)

getRenderManager(): RenderManager (the base is the lift's base position + offset, following the lift's rotation) · getSoundManager(): SoundManager (same base) · setDebugInfo(...).

PIDS scripts

A separate system

This system is mutually incompatible with PIDS Layout Editor / PIDS Modularization / PIDS JSON (EpicPuppy) and the early MTR 4 beta's info screen customization; the formats cannot be converted between each other — the barrier to entry is higher, but it can build more complex layouts.

In the pids_images array of joban_custom_resources.json, a preset object carrying scriptFiles or scriptTexts becomes a scripted preset (scriptInput / scriptRateLimit mean the same as for the other kinds; Yanyang also accepts scriptLocations to mix in C++, see mixed entries):

{
    "pids_images": [
        {
            "id": "pids_demo",
            "name": "Demo Scripted PIDS",
            "scriptFiles": ["jsblock:scripts/pids_demo.js"],
            "scriptInput": { "theme": "dark" },
            "scriptRateLimit": 0.75
        }
    ]
}

What you draw on a PIDS is polygons in the world, not a 2D canvas — elements can spill past the screen's bounds, and clipping to the screen is the script's own responsibility (when you truly need complex clipping / image processing, draw into a GraphicsTexture and blit it). Draw order is z-order: later draws cover earlier ones; by default each draw steps a tiny amount (0.0002) along z to prevent z-fighting, which you can disable with ctx.setAutoZOrdering(false) and manage manually via zOrder() (ctx.setZOrderStep(m) adjusts the step).

Dynamic textures on PIDS

PIDS can blit GraphicsTextures too: new GraphicsTexture(pids.width, pids.height) in create, then in render draw, upload(), and Texture.create().texture(state.tex.identifier).size(pids.width, pids.height).draw(ctx), and close() in dispose — the fallback when text layout can't cut it, at a cost in performance and memory.

Don't need a script? Writing only JSON fields such as background / color / fonts / showWeather / showClock / hidePlatform / hideRow / topPadding / textOverflowMode in a pids_images entry makes it a "JSON preset" — enough for simple reskins, and it's strictly one or the other with a scripted preset; the two can't be mixed.

DisplayHelper (the built-in multi-screen helper)

A ready-made solution for trains with many screens: after include(Resources.id("mtrsteamloco:scripts/display_helper.js")) —

let slotCfg = {
    "version": 1,
    "texSize": [2048, 1024],
    "slots": [
        { "name": "lcd_north", "texArea": [0, 0, 2048, 274],
          "pos": [[[-0.59, 2.125, -1.75], [-0.755, 2.03, -1.75],
                   [-0.755, 2.03, -3.25], [-0.59, 2.125, -3.25]]],
          "offsets": [[0, 0, -5], [0, 0, 0], [0, 0, 5], [0, 0, 10]] }
    ]
};
let dhBase = new DisplayHelper(slotCfg);

function create(ctx, state, vehicle) {
    state.rl = new RateLimit(0.05);
    state.dh = dhBase.create();          // Instantiates and binds the texture
}
function render(ctx, state, vehicle) {
    if (state.rl.shouldUpdate()) {
        let g = state.dh.graphicsFor("lcd_north");  // The slot's canvas (offset applied automatically)
        // ... AWT drawing ...
        state.dh.upload();
    }
    for (let car of ctx.getMyCars())
        ctx.getCarRenderManager(car).drawModel(state.dh.model, null);  // Must be drawn every frame
}
function dispose(ctx, state, vehicle) {
    state.dh.close();
}
  • All slots share one big texSize texture; texArea picks the region a slot uses (x, y, w, h).
  • pos is a three-dimensional array: each screen's four corner coordinates (top-left → bottom-left → bottom-right → top-right), in meters (divide Blockbench's 1/16 units by 16), with the origin at the train's center at floor height and +X left / +Y up / +Z backward.
  • offsets clones screens with identical content (saves texture when a row of small door screens repeats); graphicsFor(name) returns the canvas pre-shifted to the slot, graphics() the whole sheet.
  • Put the upload inside the RateLimit and the model drawing outside it — the model must be submitted every frame.
