JS → C++ migration

Turn an existing JS script into a C++ native script. The two pipelines share almost one-to-one wrapper semantics — a port is mostly renaming and re-shaping, not rewriting.

Why migrate

Read these two pages first

Before porting, read Script model and lifecycle (create / render / dispose + per-instance State is fully isomorphic on both sides) and JS getting started — this page only covers the differences.

  • One marshal instead of hundreds of reflective getter calls: on the JS side every field read is a cross-language call; on the C++ side the whole snapshot is a flat POD the script reads as plain memory.
  • Zero GC pressure: no wrapper objects, no boxed strings; draw records are bump-allocated in an arena.
  • Crash guard: a faulting module disables itself (native script faulted: module disabled) — the game never crashes.
  • New capabilities land native-first: model tint / emissive / translucent, the signal extension point, and the level crossing / fare machine / announcement block scripts (ABI 16).
  • When to stay on JS: one-off scripts, no build toolchain at hand, or very fast iteration — see the comparison table in the overview.

Lifecycle and registration

The three lifecycle functions become virtual overrides; cross-frame state moves from closure variables into the State struct. Pick the registration macro for your script kind — the resource pack declaration is the same pipeline as JS entries.

JavaScriptC++Notes
function create(ctx, state, pids)void create(PidsContext& ctx, State& state, const Pids& pids) overrideruns once before first render
function render(ctx, state, pids)void render(...) overrideevery frame (same best-effort cadence as JS)
function dispose(ctx, state, pids)void dispose(...) overridecleanup when the instance retires
closure variable surviving framesmember of the State structhost-allocated, placement-new'd; the base-class template parameter is your State type
SCRIPT_INPUT JSONapi.input()mtr::Api (ABI 8+), same resource-pack declared input

Registration: MTR_REGISTER_PIDS_SCRIPT(MyScript) — vehicles / lifts / eyecandy / PSD / level crossings / fare machines / announcements use MTR_REGISTER_VEHICLE_SCRIPT / _LIFT_ / _EYECANDY_ / _PSD_ / _LEVEL_CROSSING_ / _FARE_MACHINE_ / _ANNOUNCEMENT_. One script id per module, declared in mtr_custom_resources.json exactly like JS entries (the scriptLocations classification rules are unchanged).

No twin (port by hand)

No counterpart

These JS facilities have no one-to-one counterpart on the native side — rewrite them per the right column; the converter also leaves a TODO at each of these spots.

JS facilityManual port
MinecraftClient.* (player state, screen queries)call the same-named methods on the Java wrappers through the mtr::Api JSON bridge
JSON.parse / dynamic objectsparse with the bundled mtr::Json (nlohmann)
setTimeout / setInterval schedulingstore a game_time_millis() timestamp in State and test the delta in render
require-style importsnot needed — static linking; all SDK headers are available

Semi-automatic converter

The SDK ships tools/js2cpp.py (pure standard library, zero dependencies) to automate the mechanical parts of the tables above:

python3 native/tools/js2cpp.py input.js -o output.cpp --id mypack:pids --kind pids

It applies every rename in this page, converts forEach to index loops, TextWrapper chains to mtr::Text chains, property accesses to getters, moves obvious module-scope variables into State fields (type inference + state. prefix rewrite), and rewrites basic Math / console uses; genuinely dynamic parts are never silently rewritten — they all get TODO markers.

Expected output: a skeleton that compiles as-is plus a handful of TODOs. Then build it per Compilation and iterate in game with hot reload.

Cheat sheet travels with the SDK

docs/js-to-cpp.md in the SDK zip is the same table set as this page — the cheat sheet travels with the SDK for offline development.

End-to-end example

The same "first arrival" PIDS script, both ways:

let PREFIX = "";                 // module-scope constant

function create(ctx, state, pids) {
    state.ticks = 0;             // per-instance state
}

function render(ctx, state, pids) {
    state.ticks++;
    const next = pids.arrivals().get(0);
    const dest = next ? next.destination : "No train";

    new Text(PREFIX + dest)
        .pos(0, 0).size(pids.width, 14)
        .centerAlign().draw(ctx);
}
#include <mtr/script.hpp>

struct FirstArrivalState { int ticks = 0; };   // per-instance state

struct FirstArrival : mtr::PidsScript<FirstArrivalState> {
    static constexpr auto ID = "example:first-arrival";

    void render(mtr::PidsContext& ctx, FirstArrivalState& state,
                const mtr::Pids& pids) override {
        state.ticks++;

        const auto arrivals = pids.arrivals();
        mtr::StrView dest = arrivals.size() > 0
            ? arrivals.at(0).destination() : mtr::StrView{"No train"};

        mtr::Text::create()
            .text(dest.str().c_str())
            .pos(0, 0).size(pids.width(), 14)
            .center_align().draw(ctx);
    }
};

MTR_REGISTER_PIDS_SCRIPT(FirstArrival)
  • The logic lines up row by row: the null check on get(0) becomes a size() > 0 guard (JS get returns null out of range, C++ at throws — see Data snapshots for the semantics).
  • Timing.now()-style clocks all become snapshot accessors; the closure variable state.ticks stays in State as-is.
  • On the resource pack side: during migration the JS and C++ versions can coexist in the same pack under independent ids (scriptLocations supports mixed declarations); once the outputs match screen by screen, flip the entry to the C++ side — declaration formats in Packaging.
